# Решения, допущения и что не сделано

Документ для проверяющего: что решено там, где ТЗ допускает разные трактовки, какие допущения сделаны и чего в проекте нет. Все пункты сверены с миграциями (`supabase/migrations/`), seed и кодом экранов.

## 1. Решения по неоднозначностям ТЗ

Первые пять решений согласованы со стороной заказчика, остальные приняты самостоятельно.

| Вопрос / неоднозначность в ТЗ | Решение | Почему |
| --- | --- | --- |
| **Согласовано.** «Удаляет задачи»: удалять физически или мягко? | Мягкое удаление: `delete_task()` проставляет `deleted_at` / `deleted_by`. Удалённая задача пропадает из всех списков и карточек, строка и её история остаются в базе. Прямой `DELETE` из `tasks` запрещён правами. | История статусов по ТЗ неизменяемая. Физическое удаление задачи уничтожило бы и её историю. |
| **Согласовано.** Можно ли удалить объект, у которого есть задачи? | Нельзя: внешний ключ `tasks.object_id ... ON DELETE RESTRICT`. Интерфейс показывает «Нельзя удалить: с объектом связаны задачи» (`23503`). | Иначе пришлось бы каскадно удалять задачи вместе с историей или оставлять задачи без объекта. |
| **Согласовано.** До какого момента задачу можно редактировать? | До статуса «Принята». После `accepted` любое изменение и удаление отклоняется триггером (`CR003`), в интерфейсе кнопок нет. | Принятая работа является итоговым фактом, менять её задним числом нельзя. |
| **Согласовано.** Обязателен ли исполнитель и кто им может быть? | Обязателен (`assignee_id not null`), и это должен быть пользователь с ролью `executor`. Проверяется при создании и при смене исполнителя (`CR004`). | Задача без исполнителя никуда не движется. Постановщик в роли исполнителя смешал бы роли в матрице переходов. |
| **Согласовано.** «Видит только свои задачи»: а в карточке объекта? | Исполнитель везде видит только свои задачи, в том числе в карточке объекта (RLS на `tasks`). Объекты он видит только те, где у него есть неудалённая задача. | Буквальное прочтение ТЗ. Чужие задачи на той же стройке тоже чужие данные. |
| Откуда берутся профили и роли? | Триггер на `auth.users` создаёт профиль с ролью `executor`. Роль из метаданных пользователя не читается, email в профиль не копируется. Постановщиков повышают SQL-запросом (`update public.profiles set role = 'manager' ...`). | Регистрации нет, пользователей создаёт администратор. Доверять роли из метаданных значит дать возможность назначить себя постановщиком. |
| Что именно «редактирует» постановщик в задаче? | Пока задача не принята: название, описание, объект и исполнителя. `status`, `author_id`, `created_at` клиент изменить не может. | Это все поля из ТЗ, которые осмысленно менять вручную. Статус меняется только по матрице переходов. |
| Что со статусом при смене исполнителя? | Статус сохраняется. | Задача уже на определённом этапе, сброс в «Новая» исказил бы картину. Новый исполнитель продолжает с того же места. |
| Нужен ли общий список задач? | Экран «Мои задачи» (с фильтром по статусу) есть только у исполнителя. У постановщика глобального списка задач нет, задачи он видит в карточках объектов. | ТЗ требует «Мои задачи» только для исполнителя. Для 2–3 объектов карточек объектов достаточно. |
| Кого из пользователей видит исполнитель? | Свой профиль и профили постановщиков (авторы задач, принимающие работу), но не профили других исполнителей. В истории чужой исполнитель подписан как «Исполнитель». | Исполнителю нужно видеть, кто поставил и принял задачу. Список коллег ему не нужен. |
| Каким должен быть комментарий при возврате на доработку? | Обязателен: пустой или состоящий из пробелов отклоняется (`CR002`) и в базе, и в форме. На других переходах комментарий необязателен (через API его можно передать, интерфейс спрашивает его только при доработке). | В ТЗ сказано «комментарий обязателен». Строка из пробелов по смыслу пустая. |
| Кто принимает или возвращает задачу: автор или любой постановщик? | Любой постановщик. Так же любой постановщик может править и удалять любую непринятую задачу. | ТЗ даёт права роли «постановщик» целиком и не привязывает их к автору. Постановщиков может быть несколько, и они подменяют друг друга. |
| Как деплоить фронтенд? | Vercel через Git-интеграцию, production-ветка `main`, переменные только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Миграции в облако применяются через `supabase db push`, seed выполняется в SQL Editor. | Минимум движущихся частей: секреты не попадают в GitHub Actions, деплой без отдельного workflow. |
| Видео или текст для руководителя? | Текст: `docs/explanation.md`. | ТЗ разрешает оба варианта. Текст проще проверить и обновить вместе с кодом. |

## 2. Допущения

- **Смена исполнителя не пишется в историю.** История ведёт только смены статуса, как сказано в ТЗ. Прежний исполнитель сразу теряет доступ к задаче (и к объекту, если других задач на нём нет). Новый видит всю историю задачи.
- **Объект с любыми задачами, включая удалённые, удалить нельзя.** Мягко удалённая задача физически остаётся и держит внешний ключ. Удалённые задачи не видны никому через API, восстановить их из интерфейса нельзя.
- **Пользователя, у которого есть данные, удалить нельзя.** Ссылки на профиль из `objects.created_by`, `tasks.author_id` / `assignee_id` / `deleted_by` и `task_status_history.changed_by` объявлены как `ON DELETE RESTRICT`. Пользователя, создавшего объект, задачу, назначенного исполнителем или упомянутого в истории, из `auth.users` не удалить.
- **Метки времени истории в seed разнесены на 1 мс.** Внутри одной транзакции `now()` одинаков, поэтому seed сдвигает строки истории по порядку вставки, чтобы лента шла в правильном порядке. Статусы и содержимое при этом не меняются.
- **Смена роли пользователя задним числом не проверяется.** Если исполнителя с назначенными задачами повысить до постановщика (или наоборот), существующие задачи не перепроверяются. Проверка `CR004` срабатывает только при создании задачи и смене исполнителя.
- **`security-check` оставляет данные после каждого прогона:** одну задачу в статусе `accepted` и два объекта с префиксом `[security-check] <время>`. Принятую задачу база удалить не даёт, а объекты держатся за задачи. Поэтому скрипт рассчитан на локальный стек или отдельные учётки проверки.
- **Ограничения длины:** название объекта и задачи до 200 символов, адрес до 500, описание до 5000, комментарий до 2000. Пустое название отклоняется (`23514`).
- **Ошибка «нет прав» и «не найдено» неразличимы** (`42501`), чтобы по ответу нельзя было узнать, существует ли чужая задача.
- **Исполнителей в списке выбора постановщик видит по имени** (`full_name`). Email в профилях не хранится, имя берётся из метаданных `full_name` при создании пользователя (иначе «Пользователь»).

## 3. Что не успел / не делал

- **pgTAP-тесты (`npx supabase test db`, 133 проверки) не запускаются в CI.** Локально они проходят, но в CI только `lint`, `typecheck`, `build` и `test` (vitest). `security-check` в CI тоже нет: нужен живой проект и учётки.
- **Нет e2e-тестов в реальном браузере.** Компонентные тесты vitest (41 тест) работают в jsdom с подменённым клиентом Supabase. Связку с настоящей базой покрывают pgTAP и `security-check`. Основные сценарии интерфейса (вход и редиректы, «взять в работу» → «на проверку», создание задачи, возврат на доработку, удаление, ошибка удаления объекта с задачами) один раз прогонялись вручную: настоящее приложение в jsdom против локального Supabase. Этот прогон не закоммичен, потому что ему нужна живая база.
- **Нет разделения бандла (code splitting).** Один JS-файл около 776 kB (до gzip), Vite предупреждает о размере.
- **Нет интерфейса управления пользователями:** создание пользователей и назначение роли постановщика делаются в Dashboard Supabase и SQL.
- **Нет сброса пароля** и смены пароля из приложения.
- **Нет обновлений в реальном времени.** Данные перезапрашиваются после своих действий, при открытии экрана и при возврате на вкладку браузера (поведение TanStack Query по умолчанию). Изменения другого пользователя сами по себе на открытом экране не появляются.
- **Нет пагинации,** поиска и сортировки в списках. Для объёма тестового задания это не нужно, при реальных данных понадобится.
- **Не было намеренного «отрицательного» прогона `security-check`:** не проверено на специально ослабленной политике, что скрипт действительно покажет `FAIL`.
- **Нет восстановления мягко удалённых задач** и просмотра их истории из интерфейса. Данные остаются только в базе.
- **Нет журнала прочих изменений задачи** (кто и когда поменял название, описание, объект, исполнителя). Ведётся только история статусов.
