## Что делаем
Пишем три документа, которые закрывают пункты 2–4 сдачи по ТЗ: README с запуском проекта, объяснение для руководителя-непрограммиста и список решений и допущений. Без них сдача неполная, даже если приложение работает.

## Пользователь получает
Как **руководитель-непрограммист**, я могу **за пару минут прочитать, как устроена система и почему исполнитель не доберётся до чужих данных**, чтобы **доверять решению без технических подробностей**.
Как **проверяющий разработчик**, я могу **поднять проект локально по README и увидеть, какие решения приняты и почему**, чтобы **подготовиться к созвону**.

## Готово когда
- [ ] Given чистая машина с Node и Supabase CLI, when разработчик следует README, then он ставит зависимости, заполняет `.env` по `.env.example`, применяет миграции (`supabase db push` / `supabase link`), заливает сиды и запускает `npm run dev`
- [ ] Given README, when проверяющий его открывает, then видит ссылку на приложение на Vercel, тестовые учётки (1 постановщик, 2 исполнителя), команду `npm run security-check` и предупреждение, что `service_role` в проекте не используется
- [ ] Given `docs/explanation.md`, when его читает руководитель без технического бэкграунда, then на полстраницы и без терминов (или с их объяснением) описано: как устроена система, как защищены данные (проверка на стороне базы, а не только в интерфейсе) и что исполнитель не может сделать
- [ ] Given `docs/decisions.md`, when его читает проверяющий, then там есть 5 согласованных решений (soft delete задач; объект с задачами нельзя удалить; задача редактируется до «Принята», после — только чтение; исполнитель обязателен; исполнитель видит только свои задачи) и допущения: переназначение исполнителя не пишется в историю, объект с любыми задачами (включая удалённые) удалить нельзя
- [ ] Given `docs/decisions.md`, when проверяющий ищет, что не сделано, then там есть явный раздел «Что не успел / не делал» с перечнем

## Как делаем
- README: описание, стек, локальный запуск, переменные окружения, миграции и сиды, деплой, тестовые учётки, проверка безопасности.
- `docs/explanation.md`: простой язык, аналогии («проверку делает база, как охранник на входе, а не табличка на двери»), список «исполнитель не может…».
- `docs/decisions.md`: таблица или список «Вопрос в ТЗ → Решение → Почему», затем допущения, затем «Что не сделано».
- Факты сверяем с реальными миграциями и экранами, а не с планом.

## Файлы
- `README.md` — запуск, миграции, env, учётки (новый файл)
- `docs/explanation.md` — объяснение для руководителя (новый файл)
- `docs/decisions.md` — решения, допущения, что не сделано (новый файл)
