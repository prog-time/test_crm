## Что делаем
Реализуем по согласованному плану (этапы 1–6) мини-CRM для строительной компании: постановщик ставит задачи по объектам (стройкам), исполнители берут их в работу и отдают на проверку. Логика статусов, история и права доступа обеспечиваются на уровне базы Supabase (RLS, триггеры, RPC), поэтому обойти их прямым запросом к API нельзя. Это родительская задача: работа разбита на 6 подзадач, по одной на этап.

## Пользователь получает
Как **постановщик**, я могу **вести объекты, ставить задачи исполнителям, принимать работу или возвращать её на доработку**, чтобы **контролировать ход работ на стройках**.
Как **исполнитель**, я могу **видеть только свои задачи и менять их статус по правилам**, чтобы **понимать, что делать, и сдавать работу на проверку**.

## Готово когда
- [ ] Given приложение задеплоено на Vercel, when проверяющий открывает ссылку и входит под выданными доступами (1 постановщик, 2 исполнителя), then вход работает, в базе 2–3 объекта и несколько задач во всех статусах
- [ ] Given репозиторий `prog-time/test_crm` на GitHub, when проверяющий открывает его, then в нём лежат миграции базы (`supabase/migrations/`) и README с инструкцией по запуску, а секретных ключей (service_role) в репозитории нет
- [ ] Given руководитель-непрограммист, when он читает `docs/explanation.md`, then за полстраницы без терминов понимает, как устроена система, как защищены данные и что не может сделать исполнитель
- [ ] Given проверяющий, when он читает `docs/decisions.md`, then видит решения и допущения там, где ТЗ неоднозначно (5 согласованных решений и другие), и список того, что не сделано
- [ ] Given исполнитель с anon key обращается к Supabase напрямую, мимо UI, when он пытается прочитать чужую задачу, перескочить статус, подделать историю или повысить себе роль, then база отказывает (подтверждено `scripts/security-check.ts`)

## Как делаем
- Стек: Vite + React + TypeScript, Mantine UI, react-router, TanStack Query, `@supabase/supabase-js`; Supabase cloud free tier; деплой на Vercel.
- Схема БД и права: таблицы `profiles`, `objects`, `tasks`, `task_status_history`; RLS, хелперы `is_manager()` / `current_role()`, RPC `change_task_status` и `delete_task`, триггеры на `tasks`. Миграции ведём через Supabase CLI.
- Согласованные решения: soft delete задач; объект с задачами удалить нельзя; задачу можно редактировать до «Принята», после неё — только чтение; исполнитель обязателен; исполнитель видит только свои задачи.
- Порядок этапов: 1 → 2 → (3, 4 параллельно) → 5 → 6. Работа идёт в ветках от `develop`, все PR — в `develop`.
