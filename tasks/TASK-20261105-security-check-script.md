## Что делаем
Пишем скрипт, который заходит в Supabase с anon key под реальными тестовыми пользователями (исполнитель и постановщик) и проверяет, что база отказывает в каждом запрещённом действии. Так требование ТЗ «правила работают даже в обход интерфейса» подтверждается одной командой, и это можно показать на созвоне.

## Пользователь получает
Как **проверяющий**, я могу **запустить одну команду и увидеть, что каждая попытка обойти права отклоняется базой**, чтобы **убедиться в защите данных без ручного тыкания API**.

## Готово когда
- [ ] Given исполнитель A и задача исполнителя B, when скрипт под A делает SELECT этой задачи по id, then получает пустой результат, а UPDATE не затрагивает ни одной строки
- [ ] Given задача A в статусе `new`, when скрипт под A вызывает `change_task_status(id, 'review')` или `('accepted')`, then RPC возвращает ошибку
- [ ] Given любой пользователь, when скрипт делает INSERT, UPDATE или DELETE в `task_status_history`, then каждая операция отклоняется
- [ ] Given исполнитель, when скрипт пытается обновить свою строку в `profiles` на `role='manager'`, then запрос отклоняется, а роль остаётся `executor`
- [ ] Given постановщик, when скрипт делает прямой DELETE из `tasks`, then запрос отклоняется, а задача остаётся
- [ ] Given задача в статусе `accepted`, when постановщик пытается изменить её название или вызвать `delete_task`, then запрос отклоняется
- [ ] Given постановщик, when он создаёт или обновляет задачу с `assignee_id` другого постановщика, then запрос отклоняется
- [ ] Given задача в статусе `review`, when постановщик вызывает `change_task_status(id, 'rework', '')`, then RPC возвращает ошибку
- [ ] Given все проверки пройдены, when скрипт завершается, then печатает сводку PASS/FAIL по каждой проверке и выходит с кодом 0; при любом FAIL код ненулевой

## Как делаем
- `scripts/security-check.ts` запускается через `npx tsx` (скрипт `npm run security-check`) и использует `@supabase/supabase-js` только с anon key.
- Учётки тестовых пользователей и URL/anon key берутся из переменных окружения (локальный `.env`, не коммитится), например `CHECK_MANAGER_EMAIL`, `CHECK_EXECUTOR_A_EMAIL` и т. д. В `.env.example` добавляются пустые ключи.
- Каждая проверка — отдельная функция `expectDenied(name, fn)`; PASS — ошибка от PostgREST/RPC или 0 затронутых строк.
- Нужные состояния задач (свежая `new`, `review`, `accepted`) готовим через легальные переходы RPC внутри скрипта или берём из сидов; служебные данные помечаем префиксом и soft-удаляем в конце, где это разрешено.
- `service_role` не используется.
